# recruiter-labs

Shared global instructions for every AI tool working in this repository
(Claude Code, Codex, and anything else). Only rules that apply to nearly every
task live here; everything else is loaded on demand from `.ai/`.

`.ai/` is the single canonical AI layer. No project rule, role or workflow is
maintained separately per tool.

## Where instructions live

| Location | Purpose |
| --- | --- |
| `AGENTS.md` | Global rules that apply to almost every task (this file). |
| `.ai/guidelines/` | Shared stable engineering guidance — stack detail, verification commands, tooling (`project-core.md`). |
| `.ai/skills/<name>/SKILL.md` | Shared workflows and domain knowledge, loaded only when relevant. |
| `.ai/roles/<name>.md` | Shared worker/reviewer role definitions (canonical). |
| `.ai/state/<feature>.md` | Local, untracked execution state (never versioned). |
| `docs/features/<feature>/` | Persistent, tool-neutral source of truth for what is being built. |
| `CLAUDE.md`, `.claude/**` | Claude Code adapters only: its entry point, its settings, and one thin registration file per role in `.claude/agents/`. No project knowledge lives there. |
| `.claude/skills/**`, `.factory/skills/**` | Framework/vendor skills generated by Laravel Boost from `boost.json`, one copy per tool that requires its own path. Generated, never hand-edited, never the place for project rules. |

Each rule has exactly one canonical location. Reference it from other files
instead of copying the text.

## Language

All project text must be in English: code comments, commit messages, PR descriptions, `CLAUDE.md`/`AGENTS.md` files, subagent definitions, docs, and UI copy unless a specific feature explicitly requires localization. Do not write Portuguese in any file in this repository.

## Stack

- **Backend**: Laravel (v13+) + Filament PHP (v5+) — admin/CRUD
- **Frontend**: Inertia.js (v2+) + React (v19+, with **React Compiler** enabled) — pages outside Filament's scope
- **Styling**: Tailwind CSS (v4+)
- **Client-side data fetching**: TanStack React Query (v5+) — only when needed (polling, refetch, client-side cache); the default flow is Inertia props from the controller
- **Architecture**: single monolith (no separate API/SPA)

Dependency versioning, React Compiler details and the project's verification
commands live in `.ai/guidelines/project-core.md`.

## Git rules

Never create branches, commit, or push unless explicitly asked to in that specific message. This applies to every agent (main thread and subagents) — do not commit as a side effect of "finishing" a task.

## Testing

Do not write or modify tests (Pest/PHPUnit) unless the user explicitly asks for them in that specific message. This overrides any framework or tooling guidance that asks for a test per change (Laravel Boost's "Test Enforcement", the `pest-testing` skill) and the `qa-tester` role's default usage — implementing a feature or fix is done once it works and passes existing tests, not once new tests exist for it. This applies to every agent (main thread and subagents), including `code-reviewer`, which should not flag missing test coverage as a blocker.

Running existing tests is always allowed and encouraged.

## Conventions

- Keep Inertia page files focused on page-level rendering and component composition. Move reusable or substantial UI into `resources/js/components`.
- When a file needs small local React components, declare them as arrow functions. The main Inertia page component must be declared as a default exported function.

## Documentation

### Persistent feature documentation

Approved feature documentation lives under:

```text
# Existing / as-built feature
docs/features/<feature>/
└── spec.md    # product source of truth — current observable behaviour (WHAT/WHY)

# New / planned feature
docs/features/<feature>/
├── spec.md          # required product source of truth (WHAT/WHY)
└── tech-design.md?  # optional, binding technical source of truth (HOW)
```

It is versioned project documentation shared by every AI tool and by humans. It
is **never** deleted automatically, never deleted as part of "finishing" a
feature, and is updated when reality diverges from it. See
`docs/features/README.md` for the document contract.

Implementation task decomposition is runtime execution state, not persistent
feature documentation. The `execute-feature` orchestrator derives and maintains
it only in `.ai/state/<feature>.md`; it never creates `tasks.md`.

For planned features, `spec.md` is sufficient for execution. When
`tech-design.md` is absent, the orchestrator chooses the best technical approach
from the current repository context and history. When it exists, it is binding
and must be implemented exactly; any required deviation is a blocker to
surface, not an automatic documentation correction.

### Temporary plans

Working plan/scratch `.md` files produced by a planning skill or by a session
(anywhere outside `docs/features/**`) are session scaffolding: delete them once
the plan has been fully executed. They must not end up versioned in the repo.

Beyond feature documentation, only create documentation files when the user
explicitly asks for them.

## Loading AI skills

Load a skill by reading its `SKILL.md` **only when its domain is relevant** —
loading everything on every task wastes context and dilutes the rules that
matter.

| Working on | Load |
| --- | --- |
| Executing a documented feature (`docs/features/<feature>/`) | `.ai/skills/execute-feature/SKILL.md` |
| Acting as, or delegating to, a specialised worker | `.ai/roles/<role>.md` |
| Overview, Jobs, job/application/candidate workspaces, Calendar, Kanban, hiring workflow, navigation, attention/progress | `.ai/skills/recruitment-workflow/SKILL.md` |
| `App\Ai\Agents`, criteria extraction/confirmation, candidate evaluation, fit/coverage/confidence, interview brief, AI context sanitization, AI usage or caching | `.ai/skills/evaluation-integrity/SKILL.md` |
| Commands for lint, static analysis, types, tests, formatting | `.ai/guidelines/project-core.md` |

Framework knowledge (Laravel, Filament, Inertia/React, Tailwind, Pest,
Wayfinder, Fortify) is **not** global context. It comes from the Boost-generated
skills in `.claude/skills/**` (mirrored to `.factory/skills/**`), activated when
you work in that domain, and from the Boost MCP server's `search-docs` for
version-specific documentation.

## Roles and orchestration

The canonical role definitions live in `.ai/roles/` (see
`.ai/roles/README.md`): `laravel-backend`, `filament-admin`,
`inertia-frontend`, `code-reviewer`, `qa-tester`. A tool with native subagents
registers them from there; a tool without them adopts the role in-thread by
reading the same file. Their instructions exist only once.

The main agent acts as **orchestrator**: it breaks the work down, hands each
task to the matching role, and runs verification loops
(implement → deterministic checks → review → fix) before considering anything
done. It does not implement a whole feature by itself.

Rules:

- For any non-trivial task, use the matching domain role instead of improvising
  on the main thread. Reuse these five — do not add a generic "implementer".
- A task that crosses domains runs the needed roles sequentially inside one task
  boundary; avoid fan-out that is not needed.
- Prefer deterministic verification (see `.ai/guidelines/project-core.md`)
  before spending tokens on an AI review.
- A role implements only the scope it was given; anything else it notices is
  reported, not fixed.
- Use `code-reviewer` as the verification step before finalizing changes.
- Executing a documented feature follows `.ai/skills/execute-feature/SKILL.md`,
  the single canonical description of that workflow. Nothing else restates it.
